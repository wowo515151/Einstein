Lib4 Port and Test Matrix

This matrix maps the inspected local Lib4/ source modules to the clean-room JavaScript implementation. It records module-family coverage and current tests; it does not claim method-by-method parity with the Python package. PyTorch tensor/device semantics, CUDA devices, dtype/device mutation, autograd, and any undocumented behavior are outside this JavaScript API; supported JavaScript batch shapes are described per module. Full parity remains open until every supported Python method is mapped and compared against mathematical contracts.

Internal helper audit: _mechanics_fields_utils.py's _require_torch has no JavaScript counterpart because the library uses built-in arrays and installs no numerical dependency; _as_tensor maps to the bounded finite-array normalization used by mechanics constructors; and _check_last maps to trailing-shape validation in tensorShape. Direct tests cover Jacobian row/column order, higher-rank values, coordinate batches, and Lorentzian/positive-definite Hodge conventions.

Tensor4.transform now matches Lib4's requirement that every transformation matrix be invertible, even when all indices are upper; previously the JavaScript version accepted singular matrices for that case. Mixed-variance transformations reuse the inverse transpose across lower slots.

Additional analytic metric coverage: a Rindler-wedge fixture checks the analytic nonzero Christoffel coefficients, near-zero curvature for a nontrivial flat metric, and endpoint convergence of a geodesic mapped from an inertial Minkowski worldline. A spatially flat de Sitter FLRW fixture checks analytic Christoffel coefficients, Ricci tensor/scalar and Kretschmann scalar, plus a comoving geodesic. A Schwarzschild exterior fixture checks the vacuum Ricci tensor/scalar, analytic Kretschmann invariant, a Christoffel coefficient, and finite-difference refinement. These improve the metric-family audit without closing the broader curved-metric coverage gap.

GPU and visualization scope

src/gpu.js provides Float32 WebGPU batch dot products and bounded normalized plane-wave field sampling, with Float64 CPU paths and up to 262,144 events per batch. Plane-wave GPU dispatch is limited to a conservative phase-input envelope; GPU trigonometric accuracy remains unverified on physical hardware. It falls back before dispatch when device limits, Float32 conversion, or a conservative product bound could overflow, and also falls back on non-finite GPU output. Initialization validates shader compilation messages and releases failed devices; loss clears handles and disposal prevents reinitialization. Mocked tests cover no-device, limit, shader/pipeline failure, device loss during readback, a stale readback failure after concurrent reinitialization, disposal, temporary-buffer cleanup, and CPU fallback paths, but physical WebGPU hardware and tolerance have not been verified. This does not reproduce PyTorch CUDA/autograd. Fixed-step integration is capped at 10,000 steps and 1,000,000 output components; finite-difference step sizes must be positive and finite; parallel transport and boundary shooting have separate product limits documented in geometry.md.

The copied ThreeViz src/ tree and its MIT notice are preserved. The locally available Three.js r128 distribution and matching OrbitControls script are bundled in visualizations/vendor/ with their MIT license; the HTML loads them locally and makes no runtime network requests. Scene data tests cover ten deterministic bounded models. The playback controller has isolated tests for start, pause, frame progression, reduced-motion changes, unavailable state, and timer disposal. The application constructs labeled x/y/z axes and provides a legend for each scene's axis meanings. It constructs overlays including tubes for worldlines and paths, arrow geometry for transformed fields, a triangulated animated field slice, analytic E/B vectors and isosurface sheets, a curvature-colored embedded surface with a wireframe metric grid, and a sphere mesh for the light-cone section; selected samples remain available for point picking. The curved surface uses an explicit radial metric and Gaussian-curvature formula for its declared embedding. The light-cone, Lorentz, aberration, electromagnetic-field, causal-interval, twin-clock, charged-particle, and geodesic scenes directly use corresponding library operations. The Minkowski display now shows a straight inertial worldline consistent with its interval calculation; the velocity-addition and aberration scene composes collinear four-velocities through the relativity library and tests the closed-form subluminal result while displaying boosted star directions. The particle path integrates the declared uniform-field Lorentz force with bounded RK4. The gravitational-lensing scene traces eight 3D null rays through a softened, static weak-field metric using Connection4 and Geodesic4; tests verify inward deflection, a bounded 312-row sample, and near-zero metric norm. It is not an exact vacuum solution or calibrated astrophysical model. Other curved-spacetime scenes remain pedagogical. Local tests build all ten scenes with bundled Three.js geometry and exercise the mounted application with a simulated renderer. Actual GPU rendering, visual presentation, browser interaction, and assistive-technology behavior remain unverified.

Provenance

The inspected Lib4 directory tree contains no license file. This project does not copy Python source or bytecode; its JavaScript uses mathematical behavior and newly written code. Resolve source provenance before making external publication or source-level parity claims.
