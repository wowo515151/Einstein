GPU and CPU Backends

samplePlaneWaveBatch(events,{waveNumber,backend,gpu}) samples a normalized vacuum plane wave traveling in the positive z direction. events is a flat array of [ct,x,y,z] groups, waveNumber is positive, and each returned object has electric: [a,0,0] and magnetic: [0,a,0], where a = cos(waveNumber*(z-ct)) and c=1. The default backend is auto; cpu forces the Float64 reference, and webgpu requests the optional Float32 path with CPU fallback. Like dot products, batches are limited to 262,144 events. For GPU sampling the current conservative envelope requires 0.125 <= waveNumber <= 2 and |ct|, |z| <= 16; other finite inputs use CPU. GPU trigonometric accuracy is device-dependent and has not been measured on physical hardware. This is a specific plane-wave model, not a general field evaluator.

samplePlaneWaveGrid({shape,origin,spacing,ct,waveNumber,backend,gpu}) constructs a rectangular spatial grid at one coordinate time and samples that same wave. shape is three positive integer dimensions; origin and positive spacing are spatial triples and default to [0,0,0] and [1,1,1]. ct defaults to zero. It returns {shape, events, fields}: events is a flat Float64Array of [ct,x,y,z] groups and fields is the corresponding flat array of field objects. The z index varies fastest, then y, then x. The 262,144-point bound and representable, distinct grid coordinates are checked before allocation or GPU dispatch. Backend selection, precision limits, and caller-owned backend lifetime match samplePlaneWaveBatch; grid coordinates are currently generated on the CPU.

When passing a caller-owned WebGPUBackend, inspect lastExecution after a call: webgpu means a finite GPU result was read back, cpu means the CPU path produced the result, and none means no batch was processed (initially or after an empty batch). status describes device lifecycle and can be ready even when a particular batch fell back. lastExecution is shared mutable status; concurrent calls can overwrite it, so await calls sequentially when attributing a particular result.

Before a GPU dot dispatch, the backend estimates input-conversion and Float32 arithmetic error for each vector pair. If that estimate exceeds 1e-5 times a lower bound on the dot magnitude, the entire batch uses CPU, including near-null cancellation cases. This is a conservative screening heuristic, not a hardware-verified error guarantee; it adds CPU work before dispatch and can favor CPU for cancellation-heavy batches.

The CPU dot path normally uses Float64 arithmetic. When an intermediate product or sum overflows, or a nonzero product is subnormal or rounds to zero, it uses exact integer representations of the Float64 inputs to accumulate that dot before rounding the result back to Float64. An unrepresentable final result raises an error. This exceptional path does not address every form of floating-point conditioning loss in ordinary finite intermediate calculations.

The plane-wave shader is compiled only when a wave batch first needs it. A wave-specific compilation or pipeline failure is recorded in waveError, falls back to CPU, and leaves the dot-product pipeline available. The failure is retained until the device is replaced; a stale compilation from a lost device cannot install its pipeline on the replacement.

When the device offers asynchronous compute-pipeline creation, the backend awaits it so rejected pipeline creation triggers the appropriate fallback. It uses synchronous creation when that API is unavailable.

If a device is lost while either pipeline is being built, the pending batch falls back to CPU without waiting for the old compilation to finish. A later call can initialize a replacement device, and late work from the lost device cannot install a stale pipeline.

The CPU implementation is the reference path. minkowskiDotBatch(left,right,{backend:'cpu'}) accepts flat arrays of four-component vectors. Batches are bounded to 262,144 vectors to constrain CPU work and GPU buffers. Optional WebGPUBackend lazily requests an adapter and device and runs a Float32 compute shader for batches. Inputs that round outside finite Float32 range, nonzero terms with subnormal Float32 operands or products, and batches whose conservative dot-product bound could overflow Float32 use the CPU path; non-finite GPU outputs also fall back to CPU. Initialization validates shader compilation when the implementation exposes compilation messages and releases a device if shader or pipeline setup fails. Before allocating, the backend checks storage-buffer, buffer-size, workgroup, and workgroup-count limits; unsupported batches use CPU. If WebGPU is absent, device creation fails, or the device is lost, the function falls back to CPU. Device loss clears stale handles, and a late failure from an old device cannot release a replacement device initialized concurrently. Readback failure releases its temporary buffers; dispose() releases a retained device and prevents reinitialization. The minkowskiDotBatch convenience function disposes the backend it creates after each call; pass a gpu backend to reuse it across calls and dispose that caller-owned backend when finished. GPU output is lower precision and is not promised bit-identical to CPU output. Cancellation and device-specific Float32 behavior can still affect results. Device limits and Float32 rounding make it unsuitable for precision-sensitive tensor inversion or curvature calculations.
